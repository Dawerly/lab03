## Завдання та реалізація

Створено незмінну модель IoT-сенсорів та чисті функції оновлення:
- `Reading(observed_at, value)` — показ сенсора;
- `Sensor(id, kind, readings, labels, config)` — сенсор із показами;
- `add_reading` — додати показ через конкатенацію tuple і `replace`;
- `add_label` — додати мітку через об’єднання frozenset і `replace`;
- `update_config` — змінити конфігурацію через новий словник і `replace`.

Обидві сутності — `@dataclass(frozen=True, slots=True)`.
Покази зберігаються у `tuple[Reading, ...]`, мітки — у `frozenset[str]`.
`Sensor.__post_init__` обгортає **копію** конфігурації у `MappingProxyType`.
Ключі конфігурації — рядки; значення — тільки незмінні скаляри
`str | int | float | bool`. Вкладені змінні структури відхиляються.
Покази та числові параметри конфігурації мають бути скінченними.

`object.__setattr__` використано лише під час ініціалізації frozen-об’єкта,
щоб нормалізувати колекції та скопіювати конфігурацію. Після створення
всі оновлення повертають новий Sensor. Старі Reading можна безпечно
спільно використовувати між версіями, оскільки вони також незмінні.
У межах типізованого API вхідні значення мають відповідати анотаціям.

## Додаткові вправи

1. `calibrate` — чистий перерахунок усіх показів за формулою
   `new_value = value * factor + offset`; повертає нові Reading та Sensor.
2. `rank_sensors` — адаптація конвеєра ЛР2 до frozen-моделі:
   фільтр за типом і кількістю показів → `map` із середнім →
   сортування за середнім спадно та `id` зростаюче → Top-N у tuple.

Для рейтингу потрібно використовувати сенсори з однаковими одиницями
вимірювання. `kind` передається явно. `average_reading` повертає 0.0
для порожньої історії. `min_readings` і `top_n` мають бути невід’ємними.
Час показу зберігається як переданий рядок; джерело часу не викликається
в чистому ядрі. Вхідні записи рейтингу та їхній порядок не змінюються.

## Хешованість

`Reading` хешується за своїми полями. У Sensor поле `config` оголошене
`field(hash=False)`, оскільки MappingProxyType у Python 3.11/3.12 не
хешується. Конфігурація залишається частиною порівняння `==`.

Рівні Sensor мають однаковий hash. Різні Sensor можуть мати однаковий
hash, зокрема якщо різниться лише config; це допустима колізія.
Сенсор можна використовувати в set і як ключ dict. Рівність та хешованість
перевірено тестами, включно з різними конфігураціями.

Демонстрація: оригінал має 2 покази із середнім 21.00; після додавання

## Тести, типи та стиль

```bash
python -m pytest -q --durations=5 --durations-min=0
python -m mypy .
python -m black --check .
python -m ruff check .
```

Тести перевіряють відсутність мутацій, повторюваність результатів,
read-only config, копіювання зовнішнього словника, заморожені поля,
нові копії, хешованість, калібрування, рейтинг і неправильні значення.
`deepcopy(sensor)` не потрібен: MappingProxyType не підтримує стандартний
шлях deepcopy; тести порівнюють незмінні значення й окремі версії об’єктів.

## Вимірювання до і після

```bash
python -m pytest -q tests/test_performance.py --durations=5 --durations-min=0
python benchmark.py
```

У парних навантажувальних тестах створено дві моделі з 1000 показів.
Кожний тест виконує 40 незалежних оновлень зі спільного початкового стану.
До переходу на незмінність використовується `deepcopy` мутабельної моделі
з наступним append. Після переходу — tuple, спільні frozen Reading і
`dataclasses.replace`. Обидва підходи зберігають оригінал та повертають
незалежну версію.

Окремий timeit-вимір використовує медіану 5 повторів по 100 операцій.
Створення початкових даних не входить у timeit-замір. Фактичний результат
поточного запуску наведено нижче; конкретні значення залежать від машини.
Тести перевіряють результат операцій без нестабільних порогів швидкості.

```text
Показів: 1000; повторів: 5; операцій на повтор: 100
Порівняння: нова незалежна версія, без зміни оригіналу
До: mutable + deepcopy + append: 658.96 мкс/операцію
Після: frozen + tuple + replace: 2.51 мкс/операцію
Відношення часу до/після: 262.75
Це локальний вимір, а не гарантія швидкості для інших даних.
```

## Висновок

Незмінність спрощує тести й дозволяє безпечно зберігати попередні версії.
Спільні frozen Reading зменшують кількість захисних копій порівняно з
повним deepcopy мутабельних записів. Конкатенація tuple копіює посилання
за O(n), створення frozen-об’єкта та копіювання config мають накладні
витрати. Для звичайного in-place append характерний інший контракт:
зміна поточного стану. Наші вимірювання порівнюють створення незалежних
версій і не доводять універсальної переваги незмінних структур.
